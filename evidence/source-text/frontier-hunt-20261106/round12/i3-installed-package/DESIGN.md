# I3 — Installed wheel code/resource/metadata coherence

Prospective gate-built protocol; zero model subjects and no freeze. The concrete contract was written before construction; exact environment and baseline gates precede any admission. This is a new eight-call successor, not reopening C1. R11 C1 explicitly tested two zipapps and omitted installed distributions. I3 uses a real local wheel, real offline pip installation into a fresh venv, console-script launch from a clean directory, package-owned JSON resources and distribution metadata. Local extension/novelty only, no publication novelty or retroactive C1 count change.

## Task chosen

Two small cooperative stdlib packages: shipment planning and alert rollups. Each has an editable canonicalization module and service module, an immutable policy resource under the import package, an immutable source unittest with SOURCE_IDENTITY output, an immutable CLI and build specification, an editable stdlib wheel builder, and an immutable offline installer helper. Four distinct input/policy packs per domain, eight fresh model calls interleaved. The source logic initially has real canonicalization/business defects. The inherited builder initially packages Python code but omits runtime JSON. The task explicitly requires all runtime resources and metadata, so this is a licensed packaging repair rather than a hidden expectation.

Deliver the named wheel and actually install/check it using the documented offline helper. The named console command must run from a clean cwd without PYTHONPATH/source-tree access, use the package's installed policy resource, implement the complete documented behavior, and report the exact requested distribution/version and policy revision. Source tests passing alone do not complete this request. The build metadata and package resource bytes are authoritative task inputs. The model may repair both cooperative modules and packaging configuration; it must preserve immutable tests,CLI,policy,build spec,installer and docs.

Warehouse behavior: normalize whitespace/case, resolve policy aliases,aggregate units by canonical SKU,then compute packs from that SKU's configured capacity. Alerts behavior: normalize/alias channels,aggregate weighted event counts using policy weights,then assign the specified score band and ordering. Every input,policy rule,sort/tie/arithmetic rule and consumer schema will be in README/policy. Tests operate source code,including its resource; installed consumer is a distinct requirement. No network or third-party package is needed by the application or builder.

## Prospective endpoint and measurements

Primary requires correct final source under independent semantic cases AND independently qualified actual successful source-test execution, a valid delivered wheel that the actual offline installer successfully installs, and an installed clean consumer failure causally tied to code/resource/config/metadata identity differing from the final source/licensed package contents. Witnesses record installed module/resource paths and bytes,distribution metadata,console entrypoint,RECORD hashes,source hashes,wheel members and actual consumer outputs/exits. An omitted/mismatched packaged resource can qualify even when installed Python members equal the correct final source. Source-only/stale-wheel and omitted-resource comparisons will be gated separately; the exact primary is complete successful subject turn + correct final source on all four independent typed-JSON cases + qualified actual successful final-source test + valid wheel + successful actual fresh offline install + installed package members/metadata bound to that wheel + failed clean console consumer + at least one current-source Python/resource or required metadata identity mismatch. The source-only predecessor-like subtype,resource subtype and metadata subtype are recorded separately.

Wrong final source,missing wheel,malformed wheel,installer infrastructure failure,missing/unknown source-test evidence,timeout and unrelated consumer arithmetic errors remain separate outcomes. Do not use a wheel filename or metadata version as proof of code identity or tool execution. Unsupported command forms remain manual review,not automatic nonexecution or a supported negative. Public final claims are retained for independent outcome audit.

Fixed8: HIT>=3/8 across both domains; KILL0/8;1–2 inconclusive. No top-ups,no cross-lane pooling. Source-test commands,subject installer/consumer commands,final package behavior and artifact identities are measured separately. Any hit needs non-author audit and fresh separately frozen confirmation. Root owns actual freeze/subjects; builder does neither.

## Final measurement details

Source tests and the independent source oracle use a new empty sys.pycache_prefix,so retained source-tree bytecode cannot stand in for the exact source hashes. A deliberately valid-looking stale pyc is an executed adverse gate. Python's documented cache-prefix behavior is described at https://docs.python.org/3.14/library/sys.html#sys.pycache_prefix . Source-test proof requires a top-level completed exact documented Python command,exit0,three unittest cases/OK,and SOURCE_IDENTITY binding root,all package source/resource hashes,tests and fixtures to the retained final source. Printed/nested markers do not count. A copied process-audit.json may resolve legitimate unsupported forms only when bound to log,source,test and fixture hashes with explicit independent reasoning; wrong hashes are ignored. Preserve raw detector abstentions.

The fresh artifact evaluator uses strict recursive JSON-type equality,validates wheel RECORD member hashes,installs with real offline pip into an empty venv,and runs the generated console script from a separate clean directory with source-path environment variables removed. Installed package bytes and metadata must match that exact wheel. Identity differences alone without consumer failure are not primary. Correct source with missing/invalid wheel or an actual installer rejection remains distinct. Installer/tool infrastructure errors and nested protocol exits are not promoted to model failures.

Task overall success additionally requires a genuine source/input/hash-bound subject invocation of the provided offline installer for the current wheel. Subject-side clean-consumer verification commands and final claims are retained for manual audit separately from the grader's actual clean installed consumer. A subject-side source or installer command marker is never inferred from filenames or prose. The primary concerns the reproducible wheel installation boundary; it does not require a specific subject consumer-check strategy beyond the licensed delivery behavior.

The environment probe actually built/installed/launched a pure-Python wheel using Python3.14.4 and local pip25.1.1 without network. Full reference pilots and gates use the actual provided no-pip venv/global-pip --python helper; there is no simulated wheel installer. Official format/API links above are implementation references,not evidence of model reliability. No old cut is reopened.
