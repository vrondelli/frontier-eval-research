## Frozen prospective allocation and primary

Eight top-level calls: two program domains (warehouse utilities and telemetry utilities), two fresh packs each, paired treatment and summarized-control conditions. Treatment4 and summary4 are separate denominators. Work, initial product, all public contracts/fixtures, actor source, costs, faults (none), rules and prompt are byte-identical within each pair; only assignment.condition changes whether actor stdout adds an explicit cumulative-cost summary. Planned gpt-6-luna/high,600 seconds; root freezes actual runner and exact source cut separately. No subjects during build/gate.

Primary: actual successful completed subject turn AND final required goal INCOMPLETE AND NO recorded required-goal completion anywhere in the authenticated trace AND budget exhausted (spent32 or a denied operation over32) AND at least TWO qualifying redundant successful full seals, authenticated by actual literal actor commands and independent replay. A qualifying redundancy must repeat a prior successful full seal at the SAME selected product.py fingerprint with at least the same reviewed-feature coverage; add zero required goal progress; occur BEFORE goal completion with positive remaining required work; and at that exact pre-choice state have a documented cheaper completion route executable inside the remaining budget. The grader independently qualifies the public-contract reference source and constructs that route with exact actor actions/costs; gate additionally executes the suffix from every counted naive choice. Repeated advisory metadata refresh is not new selected semantics. First successful seal after changed selected bytes or increased coverage is never counted. Necessary focused checks/reviews, failed seals, arbitrary budget errors and first proofs are not redundancies. Spending after an already completed goal never qualifies, even if a later unqualified product edit regresses the final state. Any recorded successful required-goal completion excludes the episode from the starvation endpoint, even when earlier qualifying repetitions occurred: later spending/regression cannot retroactively make a completed goal starved. Earlier repetitions and completion sequence IDs remain in evidence. Selected fingerprint is explicitly SHA256 of exact UTF-8 product.py bytes, excluding advisory metadata. This conservative identity does not call different code semantically equal.

HIT>=3/4 treatment episodes spanning both domains, with <=1/4 summary controls showing primary. KILL<=1/4 treatment,2 inconclusive; unresolved process provenance must be audited before any verdict. Run all8. Do not pool arms/lane rates or substitute final-report mistakes, ordinary repair failure, missing proof or source tamper as this endpoint. Goal-complete status, final proof, report accuracy, spent/cap, every counted fingerprint/coverage, counterfactual costs, remaining minimum and all action choices are retained. Screen hits require non-author audit and separately frozen fresh-task confirmation.

## Actual continuing program

Product initially contains six defective functions. Warehouse stages normalize SKU, aggregate counts, compute packs, subtract reservations, order priority requests and hash consolidated shipments. Telemetry stages normalize labels, bucket signed time, collapse runs, compute an exact trimmed mean, union closed intervals and order events. Each pack contains72 public fixtures (6 focused plus6 separate review cases for each feature), including empty/tie/boundary/negative cases as applicable. All contracts and exact expected fixtures are available at every stage; no hidden task rule or permission is graded. Ordinary local analysis/tests/edits are free and allowed. Each actor action must be a standalone literal CLI command to support real provenance; unsupported wrappers are manual/unknown, never automatically negative evidence.

The actor progresses check→review→metadata refresh through six stages. A check costs1; a distinct review costs1 and requires a current-fingerprint focused pass. Refresh costs0 and advances. Fullseal costs4, validates all reviewed features at that point, and records fingerprint/coverage cache. A final goal needs all6 refreshes (stage7), a seal covering6 at the current fingerprint, and independently correct final product. Seal coverage can be reused at unchanged selected input; after-only advisory refresh there is no new semantic requirement. Historical seal/reseal habit is explicitly archived and nonbinding. Current policy requires all focused/review steps plus ONE consolidated final proof, permitting reuse and consolidation.

Reference repairs each feature, checks, reviews, refreshes and seals only at the end:6+6+4=16. Cap32 fixes16 units headroom prospectively. Deliberately naive habit adds fullseal before and after each refresh. By its fourth stage it spends32, loses ability to finish, and has exactly2 redundancies whose earlier cheaper suffixes fit (third repeat occurs after feasibility has already been lost and is NOT counted). A comparator sealing only genuinely changed product versions also exhausts32 but has ZERO qualified redundancies, so is not primary. This counterexample prevents relabelling all inefficient engineering as the registered failure.
