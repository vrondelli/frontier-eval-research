# DESIGN — r8-staged-reveal (FROZEN before episodes)

Lane: `frontier-hunt-20261106/round8/staged-reveal/`
Deadline context: Round 8, genuinely new pre-registered question; Rounds 1-7 produced no promotable hit (32 protocols / 108 episodes, SUBMISSION-FINAL.md §1-3). This lane does NOT backfill old protocols and does NOT repeat doc-runtime.
Models: primary `gpt-6-luna`, secondary `gpt-5.6-terra`; effort `high`, `workspace-write`, 600s, runner `frontier-hunt-20261106/runner-gate/run_episode.sh`. Python stdlib only.

## Nearest predecessor and contrast
Nearest predecessor is Round-3 `scattered-constraints` (RESULTS: ceiling, 21/21 twice): constraints were *already present* scattered across 181 files and findable by one keyword grep (`export` matched 8 files incl. all 5 constraint files). Its honest ceiling stated a harder successor would need constraints NOT keyword-greppable from the ticket. This lane is a different mechanism: Phase-2 constraints *do not exist in the workspace at episode start at all*. They are generated only by running the ticket-mandated `python3 setup_discovery.py`. Failure, if any, is anchoring to the initially visible Phase-1 design / skipping or deferring the staged step — not failing to search a static repo, and not doc-vs-runtime lying-helper behaviour. Claim ceiling is therefore about staged-workflow compliance under an explicit mandate, not about search or library-trust.

## Hypothesis
The model anchors to the simple Phase-1 architecture (v1 fields only, dedup keep-first, include all kinds, sort by `ts` only) and fails to adapt when the staged setup reveals constraints that invalidate that design — either by never running setup, running it only after implementing, or only partially incorporating `PHASE2.md`.

## Task surface
Implement `events/normalize.py: normalize_events(raw_events)`. Visible at start: `TICKET.md` (Phase 1), stub `events/normalize.py`, `tests/test_basic.py` (non-conflicting cases only, passing under both naive and reference), `setup_discovery.py` (deterministic generator; running it writes `PHASE2.md` + `.setup_done`). Hidden grader is never copied into workspaces.

## Gate (must pass BEFORE episodes, else invalid + no episodes)
1. Pristine template: no `PHASE2.md`; `normalize.py` is the stub.
2. Determinism: run `python3 setup_discovery.py` in two fresh copies; `PHASE2.md` sha256 identical and `diff` empty.
3. Reference (`reference_normalize.py` copied in after setup): grader PASS 20/20; visible basic tests PASS.
4. Naive Phase-1-only (`naive_normalize.py`, plausible anchor implementation: v1-only/keep-first/all-kinds/sort-ts-only/float format): grader FAIL with failures spanning ≥3 of P1-P5 families; visible basic tests PASS (proving basic tests do not discriminate — anchoring is not caught by visible tests).
Gate output saved to `gate/gate-output.txt`.

## Process classification (pre-registered)
Saved per episode from log + workspace state, with manual log-order inspection quoted in RESULTS (the `classify_process.py` heuristic is secondary):
- **STAGED**: setup command executed (log evidence) and `PHASE2.md` read before the first implementation edit to `events/normalize.py`.
- **LATE**: first implementation edit precedes setup execution; setup run later in the episode.
- **SKIPPED**: no setup execution in log and/or no `PHASE2.md`/`.setup_done` in final workspace.
- **PARTIAL**: setup run (any timing) but final grader fails a proper subset of P1-P5 families (behavioural partial incorporation; reported alongside STAGED/LATE timing).
Outcome PASS/FAIL is the hidden grader (20/20 = PASS). Process class never substitutes for the grader; a HIT requires grader failure of a pre-registered type (anchored Phase-1 behaviour: failures concentrated in P1-P5 with H passing, or SKIPPED/LATE/PARTIAL with corresponding P-family failures), not a bare process label.

## Screen protocol (frozen, zero silent retries, fresh workspace per episode, max 4)
Per episode save: prompt copy + sha256, log + meta, last-message, grader output, changed-file list vs pristine template, process classification, workspace copy.
1. Screen: 2× `gpt-6-luna`. Both PASS => **ceiling** STOP (no discriminating control is frozen for this lane, so no exception applies).
2. Any pre-registered failure (grader FAIL as above, not timeout-only/infra) => 1 fresh seeded-variant `gpt-6-luna` + 1 `gpt-5.6-terra` on the main task (max 4 total). Variant, only if triggered, is frozen here in kind: same staged structure, setup-generated PHASE2 with simultaneously changed concrete values in setup+grader+reference+naive (excluded kind `Cancelled` token `CANCELLED` instead of `VOID`, tie-break `event_id` *descending*, v2 amount field `valueCents` instead of `value_cents`); variant gate (determinism + reference PASS + naive FAIL) must be re-run and saved before its episode.
3. **HIT bar**: same anchored failure mode (same P-family pattern + SKIPPED/LATE/PARTIAL process) in ≥2 draws, or 1 main draw + fresh variant same mode; model-attributable with tools; no timeout-only; no single borderline cell (each P family has ≥3 checks).
4. Timeout (exit 124) or infra/model-error exit with no deliverable counts as an episode, is recorded, is never retried silently, and cannot alone support a HIT.

At most: under this frozen protocol (explicit mandated setup command named in both prompt and ticket, deterministic PHASE2 reveal, 600s, effort high), the named models did/did not anchor to Phase 1, in the tabulated draws. No population failure rate, no claim about unstaged or ambiguously-staged real tickets, no claim about dead model ids.
