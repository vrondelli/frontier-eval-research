# Existing work for a possible micro1 evaluation submission

Audit date: **31 October 2026, São Paulo**. Status: **observational discovery and targeted source review**. Authority effect: **none**. No new model experiments, assessment releases, participant collection, event registration or submission occurred.

## Finding

We already have substantially more than the ten proposed task descriptions: research protocols, generated cases, recorded model answers, executable reference models, counterexample validators, controlled grader challenges, actual database probes and reproducibility receipts. A candidate benchmark should adapt those assets rather than start ten unrelated tasks from scratch.

The main missing work is selecting distinct mechanisms, establishing each task's grading contract, retaining successful controls, and packaging a small reproducible slice. Several existing tasks are ceilings; their existence does not establish a frontier-model limitation. Open-ended creativity still needs semantic and usefulness judgments that finite execution alone cannot supply.

The earlier discussion missed both substantial existing instruments and a completed numerical successor. The five-engineering/five-creativity split remains a proposed submission organization, not a frozen task list or a pooled psychometric score.

## Revised ten-task candidate map

These are reusable **families to inspect**, not ten frozen tasks, ten proven model failures or ten released human cases. Select concrete questions only after source and grade review.

| Slot | Proposed family | What is already built | Remaining decision |
| --- | --- | --- | --- |
| E1 | Concurrent account operations | Invariant witnesses, finite interleavings, real locking probes | Define one business contract; keep overlapping account variants within one family |
| E2 | Duplicate identity and changed requests | Concurrent PostgreSQL receipts, mismatch controls, answer witnesses | Make this meaningfully distinct from E1; otherwise replace it with a reserve |
| E3 | Offline/restart and stale publication | Executable crash witnesses and code-artifact harness | Disclose environment limits and isolate durable replay from fresh-state correctness |
| E4 | Queue behavior and counterexamples | Executable oracle and actual incorrect/missing witnesses | Candidate for a narrow, already-demonstrated model limitation |
| E5 | Architecture under changing business requirements | 18-policy/five-context reference and tied/infeasible cases | Existing explicit version is a ceiling; no claim of model failure without fresh evidence |
| C1 | Preserve the function while escaping a preferred tool | Novelty depot/receipt cases, ordinary and component archives, deterministic schedule checks | Evaluate feasible operations and raw lineage; do not equate a changed schedule with useful originality |
| C2 | Construct a fault-tolerant alternative | Signal code families, semantic conflict controls, bit-level witnesses | Verify prose-to-decoder mapping and time/resource feasibility |
| C3 | Explain an anomaly and construct a feasible discriminating test | Causal rival worlds, unlisted alternatives, feasible-query checker | Permit different valid hypotheses; separate useful tests from hidden preferred answers |
| C4 | Preserve identity through destructive processing | Invention case, indistinguishable histories, assignment witnesses | Ask for a construction as well as diagnosis; some finite slices already have perfect results |
| C5 | Invent a sequential investigation policy | Eight task engine, adaptive/fixed references, saved executable policies | Preserve as control or prospectively change a real mechanism; repeating unchanged tables adds little |

The transfer distinction matters: several C slots measure constrained analytical construction. Calling all of them validated creativity measures would exceed the evidence. Useful originality needs a declared comparison repertoire, feasibility, outcome relevance and semantic review beyond table correctness.

**Reserves:** actual joint-work/repair, launch-authority counterfactuals, bead-transfer physical invention, derivation/deletion-lineage work and the Lab mechanic-construction proposals. Cooperation is already represented in the research, even if a tighter engineering-focused submission ultimately uses it as a reserve. If E1/E2 duplicate one mechanism, a reserve should replace one; five wording variants do not create five mechanisms.

Methods are experimental conditions across tasks, not necessarily separate tasks: ordinary, generic creativity, component A, component B and composition. Compare first attempts and raw ideas, include actual compute, retain no-opening and successful controls, and keep solver performance separate from grader error. Do not choose only observed failures and imply the resulting subset estimates general performance.

## What remains before a submission is ready

1. Read the challenge's authenticated Instructions tab and detailed rubric; public rules were reviewed earlier, but this audit did not gain access to that tab.
2. Freeze a compact source/rights manifest stating what predates the event, what changes during it, and exactly which files are included. Research prose/data in the novelty export use CC BY 4.0; new standalone export tools use MIT. Arcanum snapshots retain PolyForm Noncommercial and archived adapters have no new software license granted by the export. Do not copy the entire mixed-license repository into the submission.
3. Pick concrete, mechanism-distinct tasks from this map; establish ground truth where possible and an explicit uncertainty/adjudication route where not. Include valid unusual alternatives and negative controls. The author key is not automatically truth.
4. Separate development answers and known counterexamples from fresh evaluation. Previously exposed tasks/answers can demonstrate mechanisms, not supply an untouched performance estimate.
5. Standardize model invocation and runtime contracts. Preserve requested versus resolved model identity, missing provider revision/output-cap information, first attempts, failures, retries, exact prompts and actual resource use. Existing signed-in app-server access is exploratory infrastructure, not a self-contained route available to every judge.
6. Build a small clean-environment runner with dependencies, deterministic reference checks, saved examples, optional fresh-model mode and explicit cost/runtime. Package selected code and supporting files, not the multi-gigabyte assessment workspace.
7. Report per-family solving, claim and witness correctness, grader false passes/false fails, abstentions and format failures. Avoid a single creativity/engineering ranking or human-validity claim.
8. Prepare the walkthrough and short description only after the claims correspond to the frozen package. Agreement acceptance, publication and actual submission remain separate actions.
