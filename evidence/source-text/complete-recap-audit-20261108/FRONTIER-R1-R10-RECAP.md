## What really was invalid and should remain discarded

- R1 rubric: the grader imposes a secret prior-art/clone ranking rule and the author applies it non-blind. Reference-PASS/naive-FAIL arithmetic alone does not establish construct validity.
- R3 temporal leakage: the timing/cutoff interpretation produces apparent over-exclusion failures while actual leakage is0/4. The repair changes/clarifies what is specified.
- R5 conflict secondary: an unstated REQ-ID token requirement is not a licensed model failure.
- Coordinator noexec environment: inability to load an embedded native helper is an instrument/environment defect, not failed reasoning.
- Process counters: an execution regex can match a test command printed inside a README. R10 independent review corrected two such descriptions. Reading `python test_visible.py` is not executing it.
- V6 own-test quality: rejecting a naive mutant is insufficient if the same tests reject the correct reference; the old claim8/8 discriminating suites was corrected to7/8.

Retaining these corrections is good practice. They should not be resurrected to manufacture a stronger finding. Conversely, their invalidity does not erase other genuine failures.

## Why zero endpoints did not mean perfect work

The early research often studied a conjunction of circumstances, not broad task completion. For example, V6 asks for an executed self-test that passes a bad implementation while the delivered product fails. A wrong implementation with unexecuted tests does not satisfy that mechanism, even though it fails the user's software task. An honest near-optimal plan can miss an optimization goal without making a false-optimality claim. A protocol may rightly record zero occurrences of its proposed mechanism while retaining ordinary errors elsewhere.

The semantic distinction is legitimate; calling all such results `ceiling` invites an unjustified inference that the model made no meaningful mistake. Future summaries need separate columns for delivered-goal errors, mechanism occurrences, eligible exposure, unknowns and promotion thresholds.

Also distinguish three questions: does the same saved program fail the same input again; does a fresh model solve the same prompt differently; and does a changed task/tool/model condition fail? Only the first is literal artifact reproduction. A successful fresh solve does not repair the old artifact or prove its failure unreal.
