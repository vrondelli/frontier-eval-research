# E1: Concurrent allowance, duplicate identity and a hot account

Status: complete research benchmark candidate; no human release or validated hiring/creativity score.

You are evolving a transfer-admission service. Explain the design, implement it, and respond to the hot-account reveal.

F1. Accounts A and B each start with100 integer units of authorization allowance. Amounts are positive integers; only these accounts and valid request shapes are tested. This exercise models authorization, not settlement, refunds or an external payment provider. There is no day rollover in a test.
F2. A request is {key,account,amount}. key is globally unique for this exercise. Identical retries return exactly the original {status,remaining} decision, including a rejected request's historical remaining amount. A changed account or amount under an existing key returns {status:"payload_mismatch",remaining:null} and changes nothing.
F3. A newly accepted request decrements its account and adds exactly one ledger row atomically with its decision. Insufficient allowance creates a durable rejected decision. Remaining allowance must never become negative. A database error is not an accepted or rejected business decision.
F4. Write Python Service(path), apply(request)->JSON object. Use SQLite at path. The inspector independently reads these public tables: accounts(account TEXT PRIMARY KEY,remaining INTEGER); decisions(key TEXT PRIMARY KEY,account TEXT,amount INTEGER,status TEXT,remaining INTEGER); ledger(key TEXT PRIMARY KEY,account TEXT,amount INTEGER). Extra implementation tables are allowed. Initialize idempotently. No benchmark/import access exists inside the worker.
F5. Multiple fresh service processes may use the same database. The evaluator issues two overlapping60-unit requests to A, repeats each from another process, changes a payload, then requests100 from B. Three isolated repetitions are declared; these are finite correctness checks, not throughput measurements.
F6. Reveal for the explanation: a few accounts dominate traffic, lock waits rise and there are deadlock retries. Diagnose contention versus lock cycles, explain cross-account parallelism, choose a first mitigation and name a correctness/latency rollback trigger. The executable slice does not have a latency gold label.

Return task_id E1, code (the complete Service source string), and explanation. Explain atomic boundaries, identity scope, unknown-outcome replay, hot-account limitations and deployment tradeoffs. Viable architecture ideas beyond this SQLite interface may use the alternative-format review route; they receive no fabricated executable pass.

Grading: independently observed replies, on-disk accounts/decisions/ledger, both serial outcomes of the overlap, replay and mismatch behavior. Explanation quality is reviewed separately.
