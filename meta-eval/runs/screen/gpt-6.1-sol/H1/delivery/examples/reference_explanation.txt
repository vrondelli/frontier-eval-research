One BEGIN IMMEDIATE transaction covers the identity lookup, allowance check, decrement, ledger insertion and durable decision. Commit completes before the reply. An exception rolls back and propagates as a database error; it is never turned into an insufficient-allowance decision. Initialization uses idempotent schema creation and INSERT OR IGNORE, so opening a second instance cannot reset balances. The key is global across accounts: look it up before evaluating allowance and compare both account and amount. Identical retries return the stored status and historical remaining even if later requests changed the account. Rejected decisions are stored too, with no ledger row or decrement.

If a caller loses the response after commit, the caller does not know whether the operation took effect. Retry the identical request with the same key against the durable decision store. Do not mint a new key or infer failure from the timeout. A pre-commit failure leaves no partial business decision. Persistence and replication settings, retention of keys, failover recovery and backup behavior must be chosen to preserve this replay contract. This exercise has no external transfer side effect; a production settlement system would need its own durable intent and provider identity protocol.

For the reveal, increasing lock waits alone indicate contention, not necessarily a lock cycle. SQLite with BEGIN IMMEDIATE serializes writers across the database, even for unrelated accounts. In the usual single-database setup this is primarily writer contention, rather than proof of a row-lock deadlock cycle. Inspect the exact database error codes and transaction traces. Distinguish SQLITE_BUSY writer waits and deferred-transaction upgrade conflicts from genuine deadlocks involving other databases or application resources. In a row-locking deployment, capture wait-for edges and acquisition order before diagnosing a cycle; bounded backoff does not remove a cycle's cause.

My first mitigation is to keep the write transaction short and move slow computation, network work and waiting outside it, then bound admission queue depth and retry backoff. Keep retries keyed and preserve the existing atomic boundary. Hot accounts still serialize because competing operations consume the same allowance. A fair per-account queue can reduce repeated conflicts, but needs durable ownership/fencing and a global identity authority to stop the same key being admitted on two account partitions. WAL can improve reader/writer coexistence; it does not create parallel SQLite writers. If independent accounts need concurrent writes at sustained load, consider a row-locking database or account partitioning with a correct global identity design. These add operating and recovery costs; per-account queues alone do not overcome SQLite's database-wide writer limit.

For deployment I would establish a baseline and canary the mitigation. Any negative allowance, missing/duplicate ledger effect, or changed replay decision is an immediate correctness rollback trigger. A concrete latency trigger is p99 admission latency above 1.2 times the matched baseline for three consecutive five-minute windows at comparable offered load, with queue age and timeout/error rates checked as supporting signals. Rollback must drain or fence new owners before reverting so two owners cannot accept concurrently. These thresholds are an operational proposal, not a latency gold label or a measured result from this finite evaluator.
