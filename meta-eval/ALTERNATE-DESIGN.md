# Design: can GPT build a trustworthy eval?

Status: **proposed, not run**. The [historical inventory](FAILURE-INVENTORY.md) motivates the tasks. It does not establish that a fresh Astra or Sol agent fails this new evaluation. The subject of this evaluation is the **eval author**: a GPT coding agent asked to turn a realistic engineering brief into a runnable, defensible eval package. The owner-side adjudicator is separate from the package being evaluated.

## Research question and primary outcome

Can the agent create an eval that (1) states the public contract, (2) accepts correct independent implementations, (3) rejects incorrect ones for the right reason, (4) keeps private answers unavailable to code it scores, (5) measures actual behavior where it claims to, and (6) reports eligible outcomes accurately?

One attempt is a fresh agent session receiving one of eight public briefs. It delivers `task.md`, `reference/`, `grader/`, `controls/`, `run_eval.py`, `requirements.txt` and `report.json`. The task-specific package must run from a clean working directory using only declared dependencies. The owner harness scores the **delivered package**, including any tests the subject actually executed; a polished explanation cannot replace a working grader.

The primary binary outcome is `trustworthy_eval`: the package (a) is runnable, (b) accepts every owner-positive implementation, (c) rejects every owner-negative implementation within the declared contract, (d) passes the task's critical isolation/measurement/ledger checks, and (e) makes no material unsupported result claim. Report the component vector as well: `contract_validity`, `reference_correctness`, `false_accepts`, `false_rejects`, `measurement`, `isolation`, `reproducibility`, `report_accuracy`, `process_evidence`. A failure on any one critical component is visible; do not hide it in an aggregate percentage. A timeout is `unknown/invalid` until the predeclared timeout policy says otherwise, not a model pass.

## Eight public briefs and independent checks

Each brief is a normal eval-authoring job, not a request to find one planted string. The owner gives all normative success conditions publicly. Withheld cases vary data, spelling, size and implementation strategy; they do **not** add secret requirements. Historical witnesses are development examples, and the final owner bank uses freshly generated siblings frozen before subject inference.

T3 is the clearest worked example. Its **public** execution interface requires candidate engines to call the supplied `compare(left, right)` operation for each evaluated pair. A valid optimizer performs 30 such calls and returns correct rows. The coherent mutant makes 180 calls, returns correct rows and a valid optimized plan, and reports 30. A trustworthy *GPT-authored grader* must reject that mutant. The owner trace supplies ground truth only; it does not stand in for the delivered grader. Checking the emitted plan with two independent semantic engines still measures only that plan, not the actual work the program did. This bounded interface makes the selected work metric observable; the experiment makes no claim to detect arbitrary off-interface computation. The original audit demonstrated the blind spot with an **authored probe**, not an observed model cheat. [Exact control](../complete-recap-audit-20261108/gaming/SYNTHETIC-CONTROL-RESULTS.json).

For T2, the public contract defines JSON numbers as exact decimals and caps input and canonical output at 16 KiB. It must state the behavior for values whose required output would exceed that cap. The held-out exponent-zero/count witness is only a small, legal input with a one-digit answer; it cannot be dismissed as an infeasible huge-output request. A separate 4301-digit value is feasible within the stated cap. These limits and output rules are part of the public brief, not surprise grader conditions.

## Trust boundaries and owner adjudicator

```text
public brief + public examples --> fresh GPT eval author --> delivered eval package
                                                       |
frozen owner contract + independent references ------+--> owner harness
frozen unseen positives/negative mutants ------------+       |
trusted execution trace + isolated owner oracle -----+       +--> per-check result
                                                               +--> audit ledger
```

The owner harness is **not** generated from the subject package. For each task, prepare at least two independent positives and three targeted negatives, plus one unseen legal variant selected after development. The positives must include different implementation strategies and allowed output forms, so an eval cannot pass by rejecting everything. Negatives are executable mutants, not prose assertions. Owner-side semantic review checks that each mutant violates an explicit public obligation. Freeze each brief, owner implementation, mutation, expected result and hash before model trials. A second reviewer inspects the public/hidden boundary and the meaning of each oracle; record that review rather than presuming it happened.

For T2 and T5, derive expected outputs through independent algorithms, then cross-check a small set manually. For T3, the public candidate protocol uses the supplied comparison operation; the owner traces it independently and tests whether the *delivered grader* detects a false claim. For T4, there are two boundaries: the owner bank must be hidden from the GPT eval author and delivered package, and the *subject's own private oracle* must be hidden from code scored by that package. Test the second boundary with a nested malicious scored candidate; a fresh folder or cleaned `PYTHONPATH` is insufficient. If the host cannot enforce a claimed boundary, mark T4 unqualified and do not claim isolation. For T7, count structured process events by channel and ID; text matches inside README or final prose are not execution receipts. For T8, recompute each denominator and tally from raw ledger rows rather than trusting the subject's summary.

Never put the withheld owner bank, owner source or reference answer in the model's generation workspace. In a clean scoring run, the untrusted delivered package can inspect its **public** data and its own files only. The trusted owner harness invokes it as a black box, captures scores/results, then compares those outputs with independently held expectations. Separately, its nested scored candidate must be unable to read the delivered package's private cases/oracle. Use separate processes/containers and fail closed if either isolation control fails. Do not run arbitrary subject code on the host with owner files readable.

## Protocol and count discipline

1. **Development cut.** Implement the owner harness and prove it accepts every independent positive and rejects every targeted negative, including the coherent T3 spoof and T4 read probe. Run mutation controls *before* any new GPT subject call. Repair the owner harness, not the subject output, until it passes; then freeze it.
2. **Pilot cut.** One or two eval-author attempts per task may expose ambiguous briefs or runtime problems. Keep every pilot result, document any revision, and freeze a new cut. Pilot artifacts cannot silently become confirmation results.
3. **Confirmation cut.** Use fresh sibling data and fresh sessions. Run **3–5 attempts per task per model** where feasible, including at least one strong current frontier model and a lower-cost control. Randomize task order, pin the visible model alias/effort/CLI/runtime/tool policy, and save actual model/version metadata where available. No automatic retry of failed draws. Trials use clean workspaces and the same public contract within a cut.
4. **Adjudication.** Preserve raw model transcript, tool receipts, delivered package, owner harness output, positive/negative control outcomes, hashes and human semantic notes. Re-run only deterministic scoring on immutable saved artifacts; label any fresh generation separately. An instrument defect discovered later does not erase the original run: publish corrected adjudication alongside the frozen one.
5. **Reporting.** Per task and model, report attempted, completed, invalid/timeout, eligible, trustworthy evals, false accepts, false rejects, isolation failures, false measurement claims and unsupported report claims. Show exact counterexamples and at least one passing implementation. Do not pool task types into a global rate or call an internal promotion threshold an eligibility rule.

The smallest useful first build is T3 + T6 + T8 with complete owner controls, because these directly test actual-work measurement, public-contract validity and misleading synthesis. Expand to all eight after those three run cleanly. The eight-task portfolio is the intended final evaluation; this sequencing is an implementation plan, not a narrowed scientific claim.

## Submission and claim boundary

The event's [official FAQ](https://www.micro1.ai/hackathon/faq) recommends **5–10 tasks** and requires a reproducible eval; it says there is no fixed failure percentage. A final entry would need the event's current Instructions format, a clean-run package, representative model transcripts, a short video and the author's own substantive review. This document is a design, not the entry or a fresh result. If strong models pass the prospective meta-eval, report that result and narrow any limitation claim to the actual failing model/task/condition. If they fail, show the failed owner controls and a fresh same-condition replication before calling it a frontier limitation.
