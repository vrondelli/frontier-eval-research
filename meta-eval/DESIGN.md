# Historical-task replay: can GPT create a sound eval?

Status: **replication design, not yet run**. This replaces the invented-task approach in [the superseded alternative](ALTERNATE-DESIGN.md). The research subject is a GPT agent creating an eval **from scratch for the original hackathon jobs**. The agent is not asked to repair an existing grader. The [failure inventory](FAILURE-INVENTORY.md) records what went wrong in the original AI-assisted eval-building process and how often each defect appeared.

## The question

Can a fresh GPT agent take the **original evaluation jobs** and deliver a task, reference, grader, harness and result interpretation that withstand independent checks? The original work repeatedly produced incomplete contracts, incorrect references, false positives and false negatives, weak measurement and isolation, and misleading accounting. Those are failures of eval construction. A synthetic spoof only demonstrates that one grader was weak; it is not a claim that a model cheated.

The original eval author's exact conversational instruction is **not currently recovered for every case**. The saved public task prompts are instructions to the *models being tested*, not necessarily the instructions originally given to the *eval author*. Reusing a public task therefore does **not** by itself reproduce the eval-authoring condition. Each packet must record the actual authoring instruction if recovered, or label a minimal reconstruction. Never call a reconstructed brief an exact same-prompt replication.

## What the fresh GPT author receives

There are **two separate prompt conditions**. The primary condition uses the original eval-authoring instruction if recovered. Where that instruction is unavailable, it uses a minimal, source-bound reconstruction that states only the original objective and required deliverable; those results are labeled `reconstructed`, not exact replications. It adds no new quality checklist or retrospective defect hints. The original public task material is supplied where the author originally had it; availability is recorded per packet.

A **secondary coached condition** may use the new sentence I drafted: “Create a complete runnable eval for this task, including a public task statement, independent reference, grader, positive and negative controls, clean runner, and a report schema. State every graded requirement in the public task. Verify your eval before delivery.” It may also provide a source-linked sheet of past failure classes. This is deliberately stronger instruction. It could improve performance, so coached passes cannot be used to say the original condition would have passed. A failure even under coaching is informative, but it is a separate experiment.

The author receives no original private grader, private cases, reference solution, saved model answer, owner mutation bank, audit script or result label unless a recovered original instruction demonstrably supplied one of those materials; any such original exposure is recorded. It works in a new source-only workspace without access to the research repository. It gets one construction attempt and the same tool/time budget for every model within a task and prompt condition. Multiple attempts are **independent fresh sessions**, not revisions of a failed package.

## What counts as a successful replication

The GPT author delivers a complete new eval package. An independent owner harness runs it against **at least two distinct correct implementations** and **at least three targeted incorrect ones** per job. Correct alternatives are essential: a grader that rejects everything cannot pass. The known historical counterexample is a development control; independently made sibling cases test whether the eval covers the underlying rule. All owner tests must be licensed by the public task delivered by the GPT author *and* by the original job. The owner review flags any public-task change that narrows away the original obligation or adds a secret criterion.

For H5, the checker independently observes work and tries a candidate that actually does 180 comparisons while claiming 30; it also tests a legal unseen scan and a scoring-time private-oracle read. These probes show whether the **newly built eval** catches the old weaknesses. They do not assert that any original subject cheated. For H6, a 191-byte legal input containing `0e10000000000000000000` must have the same count result as plain `0`; a grader that calls both correct without checking actual output fails. For H9, every denominator is recomputed from raw records; text printed inside a README is never an execution receipt.

Owner-side reference implementations, mutation cases, expected outputs, sandbox controls and hashes must be reviewed and frozen **before** subject inference. The original weak grader is retained only as a historical comparator, never as the grading authority for the new eval. Scored candidate code runs without access to the new eval's private oracle, and the GPT-authored eval package runs without access to the owner bank. If a host cannot enforce those boundaries, isolation is `unqualified`, not a pass.

The primary outcome per fresh attempt is `complete_trustworthy_eval`: runnable package; faithful public contract; all independent positives accepted; all targeted negatives rejected; accurate measurement and isolation where relevant; complete source accounting; and no material unsupported report claim. Also report each component separately, with exact false accepts, false rejects and unknowns. No aggregate score hides a critical failure. A model can pass some jobs and fail others; report task-by-model results without pooling incompatible jobs.

## Run order

1. **Recover and freeze instructions.** For each job, locate the actual eval-authoring instruction and all materials available at that time. If unavailable, write a minimal reconstruction and label it. Hash the input packet. The new quality checklist and evidence sheet belong only to the coached condition. H8/H9 require their reconstructed briefs to be checked for fidelity before launch.
2. **Qualify the independent checker.** Prove each known historical counterexample fails the owner check, correct alternatives pass, false alarms are rejected, and the private-oracle probe cannot reach owner files. Use a separate implementation for semantic answers where possible.
3. **Run fresh author attempts.** Run the original/minimal condition first. Keep any coached condition in a separate arm with its own results. Use the same packet and budget within each arm for each model. Run several independent attempts per job, including stronger frontier models; save requested model alias, effort, runtime, tools, transcript, files, hashes and timeout state. No automatic retry or post-submission repair within an attempt.
4. **Grade and inspect.** Execute the delivered eval on the owner positives and mutants. Preserve raw outputs, per-check judgments and an independent human review of any semantic ambiguity. A failed owner checker is an instrument incident and must be fixed before it supplies a model-failure label.
5. **Report the actual outcome.** Count completed and eligible packages, false greens, false reds, boundary breaches, missed evidence, unsupported summaries and fully trustworthy evals. Split exact-instruction, reconstructed-instruction and coached results. A strong-model pass is a real negative for that condition; it does not erase historical eval-building mistakes.

This design reuses our original eval-building jobs and measures whether GPT can **build one**. Only packets with recovered original authoring instructions qualify as exact instruction replications. Reconstructed and coached packets answer related, clearly separate questions. It has not yet produced fresh GPT results or a submission-ready entry.
